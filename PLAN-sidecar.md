# Plan — Sidecar (`src/openstore/sidecar/`)

The product. Middleware only: no product info of its own, no shopping UI. One deploy serves one Merchant domain only (ADR-0007). Reads Merchant truth fresh at every Gate, mirrors moves back, signs with Merchant-held keys automatically. Serves `/.well-known/agent-commerce.json + /.well-known/ucp.json + /.well-known/jwks.json`, `/agent/*`, `/agentic/*` on the Merchant domain via reverse-proxy split.

## S1 — Skeleton + guardrail harness

- Layout `src/openstore/sidecar/` (core, protocols, consoles, verify) with no imports across the three roots in either direction — runtime, types, tests.
- Closed identifier sets enforced both directions by a build-breaking check (reason codes, scopes, statuses, routes, tool names, Ledger entry kinds), with `docs/CODES.md` generated from the enums and diffed in CI so a code that exists only in prose fails the build.
- Fail-loud error shape: structured denials carrying reason codes; no silent excepts, coercions, or defaults anywhere in v1 paths.
- Money lint (integers/paise only) + time lint (UTC) over money paths.
- Import-firewall test (lives in the sidecar path, asserts over all three roots) covering runtime + types + tests, both directions.
- Fresh `.env.example` template: this Merchant's provider keys/secrets, webhook secret, passkey RP ID/origin (= Merchant domain), sidecar signing keys, OAuth credentials, and `OPENSTORE_DEV_PROFILE_HOSTS` (empty by default, dev only, documented in place as the SSRF exception it is). Local `.env` never committed.
- DONE WHEN: empty app boots behind the proxy split; harness tests red on planted violations (unregistered code, float money, cross-root import) and green otherwise.

## S2 — Merchant-truth trait contract

- Catalogue shape: a Product Group is presentation (axes, copy, media) and a Catalogue Item is the sellable variant carrying its own SKU, price, stock, and tax fields. Every cart line, reservation, Attestation, and Quote line references a Catalogue Item; a group id anywhere a SKU belongs refuses with `variant-required` rather than resolving a size on the Consumer's behalf.
- Availability exposure rule, enforced at the boundary rather than at the door: door 2 returns exact counts per Catalogue Item over the private network and every agent-facing response carries only an Availability Bucket cut at that item's low-stock threshold, a group reading in-stock when any of its items is. The single exception is a quantity refusal the Consumer is waiting on, which names the remaining count and is rate-limited as an oracle (SPEC §5).
- Define the 9-door HTTP trait the sidecar calls and demo/real stores implement: `catalog.read (1) / stock.read (2) / reserve (3) / commit (4) / release (5) / restock (6) / orders.create+read (7) / orders.set-status (8) / quote (9)`. HMAC auth + idempotency keys (`order_id:attempt`) on every mutating door — except `orders.create`, which produces the `order_id` and therefore keys on `cart_id:attempt`, the Pending Cart being what an order is made from — closed reason codes on every refusal. Reserve is atomic compare-and-set, never negative, and also holds the Discount Code under the same idempotency key (released by `release`) so a single-use code cannot be spent twice. Sidecar owns both expiry clocks via `orders.set-status(expired)` for sidecar-created agent orders only — `pending` at 1440min with `time-limit-reached` and no stock to return, `confirmed` at the payment-link expiry with `payment-window-elapsed` and a `RELEASE`; admin/manual orders never auto-expire; Merchant never self-expires.
- Door 9 `quote` (ADR-0010): read-only, side-effect-free, deterministic. The Quote carries no validity of its own — the sidecar owns both expiry clocks and issues the checkout expiry that `expiry_utc` binds — so no clock-derived value crosses this door. In `{lines, destination, fulfillment_option_id?, discount_code?}`, out the Quote — subtotal, discount lines, fulfillment options with cost + ETA, tax lines (GST kind by place of supply), total, all paise integers with sign intrinsic (discounts negative). Side-effect-free and referentially transparent *given Merchant state*: identical inputs against unchanged state return byte-identical bytes, any number of times. Not time-invariant, and deliberately so — a price edit or an exhausted code changes the answer, which is exactly what `quote-fresh` exists to catch. The trap this wording hides is clocks: no clock-derived value may appear in a Quote, so a fulfillment ETA is a day count and never a date, or midnight turns every re-quote into a spurious `price-changed`. The sidecar computes no rates, no tax, and no discounts; an unknown code is the Merchant's refusal (`code-invalid`), not the sidecar's opinion.
- Conformance fake: in-memory Merchant implementing the trait for sidecar-side tests (stock goes negative-proof, external-sale simulation to prove re-read wins, quote determinism, and a quote that changes between calls to prove the Gate catches it).
- `orders.create+read` (door 7) carries `tracking_number` + `carrier` as optional, Merchant-set, non-PII fields once dispatched, and `invoice_number` once dispatched — dispatch is independent of order status from `confirmed` onward and refused on `cancelled` / `expired` / `failed`, so a COD order can carry all three while still `confirmed`, before `paid` exists — all pass through unchanged and the sidecar computes none of them (ADR-0020). `tracking_number` and `carrier` are agent-facing like any other order field; `invoice_number` is not, and the agent-facing order-read serializer must drop it — it reaches the Consumer through the receipt page and the Merchant's shipped notification only, because a gapless sequence is a dispatch-volume oracle (SPEC §6).
- Seed-list file format (`lists/seed.json`: name/category/region/sidecar URL/public key/protocols, plus `verified_as_of` and a self-published signature over the record) defined + validated, ships scaffolded (empty + example) — the same format an Index reads later (ADR-0022, `PLAN-distribution.md` D4), so it is fixed once here rather than twice. Reader supports direct-add URL + custom list URL, verifies the signature against the record's own public key, and refuses an unsigned or stale-`verified_as_of` entry with a named code rather than ranking it lower.
- DONE WHEN: trait conformance suite passes against the fake, including retry-safety (same key, same result), external-sale visibility (gate sees lowered `available`), quote determinism byte-for-byte across repeat calls, a quote with zero-value fulfillment and tax lines (flat-price Merchant) passing unchanged, and malformed-list rejection.

## S3 — Gate + Ledger + provider plug

- Deterministic compiler (Gate), split into `decide()` and `settle()` because Authority lands at different moments per kind (ADR-0017): `decide()` runs the fixed check order (authority-present-and-accepted + currency/Merchant/window/count/qty/blocked/tags/caps/quote-fresh/method-enabled), writes the Transcript, and permits the payment request; `settle()` verifies the Provider record, records the Authority kind and its Binding, and captures. `authority-present-and-accepted` passes at `decide()` when the kind lands before the Gate (`passkey`) and defers to `settle()` when it lands with the money (`upi-pin`), and the kind declares which — never the caller, with count/qty/caps evaluated at the Product Group so a two-per-order cap cannot be walked by taking one of each colour, all failures recorded in the Transcript with `reason_code` = first failure, closed reason codes, byte-stable transcript persisted with each decision. `cart_hash` canonical bytes frozen per SPEC §4 — covering `quote_hash`, `destination_hash`, `contact_hash`, and `fulfillment_option_id` so the tap binds the delivered total — before any translator work. `quote-fresh`: re-call door 9 with identical inputs **immediately before `RESERVE` only**, byte-compare against the pinned Quote, fail closed with `price-changed` naming the moved line; the Consumer re-taps the new number and nothing is coerced. It must never run after payment — a Merchant price edit between tap and webhook would otherwise fail a paid order and strand real money; post-payment, the pinned Quote is frozen and reconciliation is the Provider amount/currency check (`amount-mismatch`) alone. Quote inputs include the Discount Code, so quote-fresh re-validates it and an exhausted code surfaces as `price-changed` rather than a silent full-price charge. `quote-consistent`: lines sum to total, signs correct, currency matches, subtotal equals `sum(qty × attested price)` from the pinned Attestation, tax additive or informational per the Merchant's inclusive flag, and the apportionment and rounding rules hold (delivery and discounts apportioned across lines by taxable value with largest-remainder, half-up to the paise, any rupee rounding present as an explicit `round_off` line) — else `quote-inconsistent`. These rules are pinned in Merchant-site M3; the Gate only checks them, but it must check them exactly or a legal invoice and a verifiable one stop being the same document. Verifying a Merchant's arithmetic is not an engine and must survive engine-creep review. Policy edited in `/agentic`, enforced here. Dry-run mode with zero side effects.
- Append-only Ledger `RESERVE → CAPTURE / RELEASE / REFUND / REVERSAL` with escrow-zero invariant (open holds sum to zero once closed); `REFUND` carries `amount_minor` with the invariant `sum(refunds) ≤ captured` enforced at write time, so partial refunds are a generalization rather than a second path; `REVERSAL` records money removed by someone other than the Merchant as the Provider reports it — an adjudicated UPI complaint, a post-settlement adjustment, a bank correction, or a card chargeback, with the dispute's turnaround deadline carried alongside — bounded by neither invariant — it is written even when it drives net cash negative, because money that has already left must be recorded; negative net alerts, never refuses. Paise integers; one idempotency key per attempt with unique constraint + atomic stock decrement (`WHERE available >= qty`) closing read-then-act races (50-concurrent-on-5-units yields exactly 5 `confirmed`, stock never negative).
- COD path (ADR-0018): the Ledger's entries are about money only, stock is held by door 3, and the two stop being one act. `cash-on-delivery` writes nothing at order and a `CAPTURE` with no preceding `RESERVE` at collection, which the invariant permits because it quantifies over reserves — no money is held across the delivery, because no available UPI primitive holds it. A `sold-out` failure closes no hold because none was taken, while `amount-mismatch` releases the one it had.
- Provider trait (`make-link / check-status / cancel / refund`, plus an optional declared block capability `block / capture-block / release-block` that no adapter declares and no path consumes in v1 — a seam left open for ADR-0024's repeat-purchase work, not a Reserve Pay COD hold, which ADR-0018 retired) with fake + Razorpay in v1; Justpay/Airpay later in the same shape. Each adapter declares its method set at boot; the Merchant enables a subset in `/agentic`; `method-enabled` refuses anything else with `method-not-supported` naming the enabled set (ADR-0013). Razorpay declares UPI in v1, fake declares everything. Webhooks: HMAC on raw bytes, `event_id` dedupe, amount/currency reconcile vs order (mismatch → `failed` + `RELEASE` + `amount-mismatch`); provider decides the money-moved fact only, never authority.
- DONE WHEN: golden decision vectors pass byte-identical (core Transcript bytes); a `sold-out` failure writes no `RELEASE` and the trait refuses one if attempted, while an `amount-mismatch` failure releases exactly its own hold; a `cash-on-delivery` order writes its first Ledger entry at collection and nothing at all on RTO, and writes no Ledger entry of any kind at order time; ledger invariants hold under replay + concurrency tests including over-refund refusal (`sum(refunds) ≤ captured`) and a `REVERSAL` after full refund landing net-negative and alerting rather than refusing; a quote that moves between pin and capture fails with `price-changed` and moves no money; a disabled method refuses naming the enabled set; webhook forgery/replay/reorder tests pass; crash-mid-link adopts via `check-status` instead of double-creating.

## S4 — Authority + orders

- Authority as a closed set (ADR-0017): `upi-pin` (default — the payer authenticates in their own PSP app against a named payee and an exact amount; the basket binds by reference through the Quote the approve page rendered, and the Provider's signed record closes the chain), `passkey` (strongest binding, opt-in), `confirmed-intent` (`upi-verify` or `passkey` only — an OTP to a Contact Point is not a member, since it binds no funding instrument), `mandate` (defined, registered, refused). Each Authority is recorded with its Binding — what was bound (`cart`/`amount`/`none`), by whom (`payer-device`/`payer-bank`/`merchant`), how — and the Merchant enables which kinds it accepts alongside its payment methods. `consumer_id` is `HMAC(deploy_pseudonym_key, payer_handle)` for every kind, per-Merchant-domain and never a cross-merchant identifier, with the payer handle plaintext living only in the Merchant order row (ADR-0011).
- Passkeys, as the `passkey` member: per-domain enrollment (ADR-0008), performed *inside* the first approve ceremony as one enroll-and-tap page so a first-time Consumer never makes a separate signup visit, executed as a single WebAuthn `create()` whose challenge *is* the `cart_hash` + amount + expiry binding with UV required, which authorizes the spend only where the response carries an attestation statement signing over `clientDataHash`; under `none` nothing in the response is signed, so the sidecar requests attestation, verifies it, and falls back to an immediate `get()` over the same challenge when it cannot get one (Transcript records `ceremony = enrollment` vs `assertion`, distinct from the Authority kind), + per-spend tap bound to exact `cart_hash` + amount + expiry (UV on, challenge binding, sign-count tracked with warn-on-reset, never hard-lock). Virtual tap in tests runs identical checks with test keys.
- Agent admission, two routes and one authority (ADR-0012): Merchant-issued OAuth client-credentials for allowlisted agents, and self-registration for strangers — fetch the Agent Profile from its well-known URL, pin its ES256 JWKS, verify the signed request on every call, issue a short token on the spot. Signatures are RFC 9421 over method/target/`Content-Digest`/`created`/`expires` with a nonce and a short window (replay dies here, not in review); `agent_id` = RFC 7638 thumbprint. The profile fetcher is an SSRF sink and is hardened as one: HTTPS only, public IPs only, loopback/RFC1918/link-local/169.254.169.254 refused, resolve-then-pin against DNS rebinding, no cross-host redirects, size + timeout caps, and its own registration rate limit. Dev-mode exception for the compose demo (ADR-0012): `OPENSTORE_DEV_PROFILE_HOSTS` admits named hosts only, metadata IP still refused, every use logged and surfaced in health + console banner, boot refused if it is non-empty while live provider keys are present. Same four scopes either way (`search / build-basket / start-checkout / confirm`); `confirm` without a fresh tap is rejected either way; no tier unlocks money. `cancel-order` sits at `start-checkout` and is pre-money only — own orders, `RELEASE` where a hold exists, `cancel-not-allowed` at or past `paid` — so an agent can put down a basket it built instead of parking stock until the window lapses. Rate-limit tiers (self-registered low, allowlisted high) and a Merchant blocklist that refuses registration; per-IP limits plus a separate throttle on tap-token issuance and approve attempts. Dual identity on every order: `consumer_id` + `agent_id`, independently revocable; gate needs both.
- Permissions: standing approval covers reads/drafts only; any cart-with-spend, checkout, or place-order needs a fresh Allow-once modal plus a fresh tap. Tap delivery at `/agentic/approve?t=<one-time-token, 5-min, single-use>`, including the `Have a code?` field for `private` Discount Codes — applying one re-calls door 9, re-renders the total, and rebinds the ceremony to the post-application `cart_hash` before any signature, so the code never transits the agent (ADR-0015) — with a resume URL carrying an unguessable, single-use, session-bound resume token that resolves to `order_id` + `chat_thread_id` server-side — never those two as bare URL parameters, which would let anyone holding the link resume someone else's checkout: sidecar restores the cart snapshot, chat restores its thread, equality asserted.
- Orders in the Merchant book via the trait: Pending Cart (₹0 agent basket) is distinct from a `pending` order row. `pending` (24h, ₹0 moved) → `confirmed` → `paid` / `cancelled` (pre-money, `RELEASE` + link `cancel`) / `expired` (two sweeps, one status: `pending` at 24h with `time-limit-reached` and untouched stock, `confirmed` at the payment-link expiry — default 15 min, never beyond the Provider's link lifetime — with `payment-window-elapsed` and a `RELEASE` returning held stock, so an abandoned tap cannot hold inventory) / `failed` / `refunded` (post-money, full or partial, `REFUND` with `amount_minor` + per-line `restock`) / `completed` (observed); tap vs expiry serialize on `orders.set-status`. Refund and shop-reject are both triggered by demo-admin calling the sidecar over HMAC (refund: reason + amount + per-line restock flags; reject: reason), never by a local write on the Merchant side — the sidecar owns the hold and the serialization point, so shop-reject, tap, and expiry sweep all serialize on one `orders.set-status` key. Destination, Contact Point, and options ride inside the order row as plaintext (the only place they exist as plaintext), with a Merchant-set retention window and an erasure action; evidence commits by salted hash (ADR-0011). Refund carries `amount_minor` + per-line restock flags; full vs partial is derived from `refunded_minor`, never a ninth status.
- DONE WHEN: happy path passes for `upi-pin` and for `passkey`, each recording its own Binding; a `upi-pin` order whose payer declines releases its hold inside the collect window and the SKU is immediately buyable again; a hold cannot be created without spending an approve token, and token issuance throttles hold creation under load; a Destination edit after the approve page rendered invalidates the token even though the total did not move; an amount change owes a fresh Authority under `upi-pin` while a Contact Point fix does not, and both re-hash; `consumer_id` is stable across two orders on this domain and differs for the same payer handle under a second deploy key; no payer handle plaintext appears in any Transcript, bundle, or log; tampered/replayed/stale assertions rejected with codes; a replayed signed agent request is refused outside its window and by nonce reuse; profile URLs pointing at loopback, RFC1918, and the cloud metadata IP are each refused before any fetch; the dev allowlist admits exactly its named host and nothing else in that range, the metadata IP stays refused even with the allowlist set, boot fails when the allowlist meets live keys, and the same host refuses with the flag off; an abandoned `confirmed` order releases its stock at link expiry and the SKU is immediately buyable again; a first-time Consumer completes enroll-and-tap in one ceremony where attestation permits and in two named, counted prompts where it does not, and a response with an empty `attStmt` is never accepted as an authorization; no agent-facing payload anywhere in the suite carries an exact stock integer except a waited-on quantity refusal; a private code applied at the approve page changes the total and the tap binds the new one, while the same code presented through the agent refuses as plain `code-invalid`; repeated wrong codes are throttled and indistinguishable from each other; a stranger agent with a valid Profile transacts end to end without any prior Merchant action, and a blocklisted one is refused at registration; rate-limit tiers enforced under load; expiry sweeper marks `expired` with nothing moved; revoked-credential orders refuse; per-domain enrollment stated in UX copy.

## S5 — Tight receipt + checker + manifests

- 5-section bundle (bought / tapped / decided / told / moved): hash-chained, Merchant-ES256-signed, no Merkle in v1 (ADR-0009). `tapped` carries the Authority kind and its Binding verbatim (ADR-0017), and the verifier prints both rather than reporting an unqualified "verified" — the honest claim for the default kind is tamper-evident throughout, third-party attested at the money step by the payer's own bank, and buyer-attested over the basket only under `passkey`. `bought` carries the Quote breakdown verbatim (so the receipt shows shipping and GST as the Consumer saw them) and commits to Destination and Contact Point as `HMAC-SHA256(order_salt, canonical bytes)` with the salt held only in the Merchant row and never in the bundle, so erasure makes the commitment permanently unopenable (ADR-0011). The PII binding is therefore an online check: offline verify covers the chain, signatures, and every non-PII fact and reports those two sections `unopened` rather than failing. Each order pins the Attestation hash (`digest` per SPEC §4) it used so later edits can't rewrite history. Refunds version: v1 bundle stays verifiable, refund appends `moved` + fresh signature as v2. Bundle carries its JWKS snapshot so offline verify is really offline; opens by unguessable 128-bit receipt ID, no login.
- Offline CLI verifier (exit `0`=valid, `1`=tampered naming the exact link, `2`=untrusted-key — including a key revoked before the bundle's timestamp, while bundles signed before revocation stay valid per ADR-0014), ID-addressed browser viewer, public JWKS, discovery manifests (agent-commerce + UCP), per-item signed attestations over `{sku, price, tags, digest}`.
- DONE WHEN: clean bundle verifies; 1-digit-tampered bundle fails naming the exact link; a bundle whose order row was erased still verifies and renders Destination as `erased`, while an altered row renders `tampered`; a partial refund produces v2 with `Refunded ₹X of ₹Y` and v1 stays verifiable; a bundle signed by a since-revoked key verifies if signed before revocation and fails `untrusted-key` if after; fixtures pinned; viewer checks against the same vectors; live keys refused at sidecar boot.

## S6 — Protocol plugs + proof

- Thin translators MCP (live) + UCP/ACP/AP2 over the same core: validate foreign envelope → core calls → translate back. Foreign direct-checkout-inside-AI maps to our approve handoff, which is UCP's own buyer-escalation path rather than a departure from it — implement the embedded binding so the ceremony renders inside the agent surface instead of as a browser bounce, and verify the profile well-known path against the published spec rather than against our spelling of it. A fresh Authority stays mandatory; completion with no handoff at all is phase-two. An instrument outside the Merchant's enabled method set maps to `method-not-supported` naming what is enabled (ADR-0013); a delegated agent-held payment credential is refused on purpose, not unimplemented. UCP's totals breakdown maps 1:1 onto the Quote, so no translator carries pricing logic. No second checkout, ledger, or receipt anywhere.
- One golden end-to-end replay per protocol (search → allow → cart → tap → fake-UPI → receipt → verify), core Transcript pinned byte-identical in CI (envelopes differ, core decision bytes don't). Demo toggle replays the same flow through the selected envelope with conformance badges that state their deviations inline — capability supported / redirect-only completion / enabled instruments — so the badge never reads as unqualified conformance.
- DONE WHEN: identical core transcript verifies through all four envelopes; the badge's deviation text is asserted present in every golden replay; unknown/legacy shapes rejected with codes, never executed.

## S7 — Mount + Merchant console

- Same-domain split via reverse proxy (proxy owns TLS; dev ships a reference `Caddyfile`): `/ → store`, `/.well-known/agent-commerce.json + /.well-known/ucp.json + /.well-known/jwks.json + /agent + /agentic → sidecar`. One origin for passkeys, separate containers/deploys.
- Minimal `/agentic` console: key enrollment/rotation/revocation + encrypted export (ADR-0014), provider secrets + enabled method set, policy CRUD + per-policy Exposure (which policies are public to agents), agent allowlist/blocklist over Agent Profiles, attribution panel (agent-sourced orders and revenue by `agent_id` over a date range), order lookup, receipt access by ID, PII retention window + erasure action. Shop ops (catalog/stock/fulfilment) never live here — that's demo-admin.
- Serve `/agent/feed.json`: read-only export of the exposed catalogue in the Merchant Center product-data attribute names SPEC §3 fixes (`id`, `item_group_id`, `title`, `link`, `image_link`, `availability`, `price`, `brand`, `condition`, `color`, `size`), one entry per Catalogue Item grouped by `item_group_id`, availability mapped from the Availability Bucket into the reader's published enum — `low-stock` folds into in-stock, since it is not a member and an invented value fails the only reader that matters — and never a count. Stable public URL with `Last-Modified`/`ETag` so a registry can fetch it on a schedule. No crawling, ranking, or auto-submission — the Merchant registers the URL, the sidecar never submits. Feed depth beyond this is phase two (`PLAN-distribution.md` D1).
- DONE WHEN: proxy-split compose boots; console completes key enroll → export acknowledged → policy edit → exposure check → method enable → agent blocklist → attribution read → receipt open by ID with zero shop-ops controls present; feed validates against the target schema and contains only exposed items.

## S8 — Install, keys, and operations

The phase that decides whether a Merchant who is not us can run this. Everything here is a gate on adoption, not on correctness, which is exactly why it gets a phase instead of a wish.

- `openstore up <domain>`: writes compose + the reference `Caddyfile` + a fresh `.env` from the template, generates the signing key, prints the encrypted key export and refuses to proceed until it is acknowledged as saved, prints the `/agentic` first-run URL. No hand-edited YAML before first boot.
- Public demo target: Fly.io as three apps (`edge` running Caddy, `store`, `sidecar`) over 6PN rather than Fly's single-app process groups, since Fly secrets are app-scoped and a single app would leak sidecar secrets into the store Machine's environment (ADR-0019). Same mount-path contract as compose (SPEC §10); `edge` is the only app with a public `[http_service]`. Demo domain is Fly-issued (`*.fly.dev`); no custom-domain binding required.
- Key lifecycle end to end (ADR-0014): `kid` + `not_before` + `revoked_at`, additive rotation, JWKS publishes all non-expired keys, history never re-signed, restore-from-export path tested.
- Health + observability: `/healthz` + `/readyz`; structured money-path log line per decision (order, agent, consumer, reason code, duration — never secrets, never PII plaintext); counters for gate refusals by reason code, tap outcomes, provider webhook lag, reconciler drift.
- Dispute intake: Provider dispute/reversal webhooks post `REVERSAL` + Timeline event; evidence pack export by receipt ID, PII-free by construction.
- Backup + restore drill: Ledger, orders mirror, keys. A restore that loses a Ledger entry must fail loudly rather than reconcile silently.
- DONE WHEN: a clean machine goes from `openstore up` to a verified receipt without editing a file by hand; key rotate → new receipt → old receipt both verify; revoke → post-revocation signature fails `untrusted-key`; restore-from-export signs again; a killed reconciler shows up in counters rather than in wrong sales; backup/restore drill passes with a planted missing Ledger entry failing loud; the three-app Fly demo boots a verified receipt end to end through `edge`'s public hostname, and `store`'s Machine environment contains no sidecar secret (provider keys, signing key) at any point.
