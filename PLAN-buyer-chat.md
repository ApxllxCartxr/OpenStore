# Plan — Demo Buyer Chat (`demo/buyer-chat/`)

Surface 3. Proves the Consumer flow end to end. Claude-like chat over Ollama (swappable model) with tool calls. Air-gapped stranger: own folder/process/deps/DB (chat sessions only), zero sidecar/merchant-site imports, HTTP-only, admitted like any external agent — by its own published Agent Profile (ADR-0012), with the Merchant-issued OAuth client as the allowlisted alternative. The chat UI is dumb on purpose — convenience is sidecar-engineered (SPEC §11), the agent renders verbatim.

## B1 — Chat scaffold + model seam

- Web chat (threads, streaming text, Claude-style cards/modals widgets) + model seam (Ollama default, swappable without touching flow code). Own session DB holds threads/display only; no carts, no money state, no Consumer PII store — the cart lives in the sidecar (Pending Cart + order row), chat cart-ops are calls not local state. Destination and Contact Point are collected in B3 and held in memory for the length of that checkout only: posted to the sidecar, never written to the chat DB, never logged, dropped on thread end. An agent that persists them has become a place PII leaks from, which is the thing the air-gap exists to prevent.
- Agent identity material: an ES256 keypair generated at first boot and stored outside the session DB (env-referenced key file, gitignored, regenerable), published as an Agent Profile at this chat's own well-known URL with its JWKS, rotated additively by `kid` like any other signer. The chat is a signer now, not just a caller, and a signer with no key story is a demo that cannot re-register after a container rebuild.
- Tool-calling loop with bounded steps and a closed action set that matches the flow it actually drives, each action mapped to the scope it needs: `search` + `read-item` (scope `search`), `add-line` / `remove-line` / `set-destination` / `set-contact` / `choose-fulfillment` / `apply-public-code` (scope `build-basket`), `start-checkout` (scope `start-checkout`), `place-order` (scope `confirm`, and only ever by handing the Consumer an approve URL), plus `order-status` and `request-refund` (reads). Model proposes, deterministic code validates against real Merchant data before anything is shown or sent.
- DONE WHEN: chat boots alone against a stub tool server, step caps enforced, malformed model output rejected with a named error and no state change; a rebuilt container re-registers with the same key from its key file; a planted write of a Destination or Contact Point into the session DB fails the build, because a claim about not storing PII with no test behind it is just a sentence.

## B2 — Direct-add + contacts

- Paste-Merchant-URL direct-add: fetch sidecar card, show name/category/key/protocols, save as contact. A Consumer-pasted URL fetched server-side is the same SSRF sink the sidecar hardened against strangers (ADR-0012), pointed the other way, so the same rules apply here: HTTPS only, public IPs only, loopback/RFC1918/link-local/169.254.169.254 refused, resolve-then-pin, no cross-host redirects, size and timeout caps.
- Merchant key trust is trust-on-first-use and pinned: the card's JWKS is stored with the contact at add time, and a later fetch presenting a *different* key for a known contact warns loudly and blocks spend rather than silently accepting it — silent key acceptance is how a hijacked domain gets paid. Rotation is normal, though (ADR-0014), so verification is `kid`-aware: an unknown `kid` triggers one JWKS refetch against the pinned domain, and only a key that fails to appear there is treated as a hijack. Admission is self-service (ADR-0012): the chat publishes its own Agent Profile at a well-known URL with its ES256 JWKS, signs its requests, and gets a token from a shop it has never met — no Merchant action first. The Merchant-issued OAuth client path stays supported for the allowlisted case. Consumer enrollment is not a step here: it happens inside the first approve ceremony (enroll-and-tap), and copy states one enrollment per shop (roaming five shops = five taps, not five signups). Custom list-URL support + baked-in scaffolded seed file (empty + example). No crawler, no ranking.
- Contact = one Merchant route (URL + credential + standing read approvals for reads/drafts only). Forgetting a contact deletes the local bookmark only and revokes nothing server-side; server revocation is separate and authoritative.
- DONE WHEN: unknown-URL, tampered-card, and dead-sidecar cases each fail with a named reason; a valid add completes against a shop with no prior knowledge of this chat, using only the published Profile; a blocklisted Profile is refused with the sidecar's reason; nothing touches sidecar code.

## B3 — MCP shopping flow (live)

- Search → permission modal showing the exact request JSON with `Allow once / Always allow (reads only) / Decline` → SpoiledDuckie result cards with filters (colour/tag/price), an option picker over the Product Group's axes that must resolve to one Catalogue Item before `ADD` is offered (unresolved or group-level adds refuse with `variant-required`; the chat never picks a size for the Consumer), add-ons that attach to a named parent line at the moment they are added (an Add-on is a composite supply, never a standalone line — an unparented one refuses with `addon-without-parent`), stock pills (`in-stock / low-stock / sold-out` — the only stock fact the chat is ever given, since exact counts stay merchant-side; a waited-on quantity refusal is the one place a number appears) and `ADD` → one bag-yes modal for spend, whose copy grants a *scope* and never an amount ("this shop may build a paid basket"), because no total exists yet and a modal that reads like an amount approval teaches the Consumer to click through the tap that is one → Destination + Contact Point collected once (typed by the Consumer, never invented by the model) → fulfillment option picked from the Merchant's returned list → optional `public` Discount Code field (private codes are deliberately not accepted here — the card says so and points at the approve page, ADR-0015) → checkout card rendered **verbatim** from the Merchant-signed Quote (items, discount line if any, shipping with ETA, GST lines, total, the Merchant's enabled payment methods, `Place order`, expiry countdown from `expires_at`). The agent never sums, estimates, or re-labels a line.
- Pre-display signature check on every Merchant-signed payload; mismatch blocks Place order with `signature-invalid`. `sold-out / blocked / cap / price-changed / code-invalid / destination-unserviceable / method-not-supported / variant-required / addon-without-parent / quote-inconsistent / payment-window-elapsed` show the sidecar's exact fix — `code-invalid` says only that the code did not apply, because a chat that explains *why* is a code oracle with a friendly face; `price-changed` re-renders the new Quote and requires a fresh tap rather than quietly proceeding. Agent-side totals never exist.
- DONE WHEN: golden MCP transcript passes; edited-total, moved-quote, and expired-offer variants block with codes; the rendered breakdown is asserted byte-equal to the signed Quote line for line; standing approval never covers a spend step (tested).

## B4 — Tap + pay + receipt without context loss

- `Place order` opens `/agentic/approve?t=<one-time-token, 5-min, single-use>` (same-domain tap ceremony, virtual tap in demo with test keys) then auto-returns via a resume URL carrying an unguessable, single-use, session-bound resume token (never bare `order_id` + `chat_thread_id`, which would let anyone holding the link resume someone else's checkout — the same IDOR the storefront's order lookup was fixed for) that resolves to `order_id` + `chat_thread_id` server-side, restoring the exact state: sidecar restores the cart snapshot, chat restores its thread, equality asserted. Fake-UPI link → marked paid → signed webhook → receipt.
- Status widgets for every end with door + reason + next step: `cancelled` (pre-pay, free), `failed` (`sold-out`/`amount-mismatch`, pick again), `expired`, which now has two faces and two messages: the `pending` Quote-validity sweep at 24h ("re-add, don't re-search" — nothing was held, nothing was lost) and the `confirmed` payment-window sweep at link expiry ("your hold was released, tap again" — stock went back on sale and may not still be there), `refunded` (amount back — full or partial, shown as `Refunded ₹X of ₹Y` with per-line restock — new receipt v2, v1 stays verifiable), `refund-requested` visible in chat. Chat polls order status through its closed action on a backoff; the response carries status, reason code, timestamps and the receipt link only — never Destination, Contact Point, or line-level PII — so `order.changed` staying sidecar-only is not the only thing keeping PII out of the chat. Failures name the exact door + reason. Zero re-login, zero re-search after tap — asserted, not hoped.
- DONE WHEN: tap-to-paid round-trip preserves exact state; expired and declined paths message correctly; all receipts marked demo with live-key refusal owned by sidecar (chat mirrors display-only).

## B5 — Protocol toggle + smoothness gates

- Header toggle `[MCP|UCP|ACP|AP2]`: MCP drives live; the other three replay the identical golden charm-to-receipt flow through their translators with envelope + shared core transcript + conformance badge side by side. The badge shows its deviations inline — capability supported, redirect-only completion instead of native in-agent completion, and the Merchant's enabled instruments — so a reader is never told this is unqualified conformance.
- Smoothness gates (red on breach): one Allow-once + one tap per spend, no re-login/re-search across tap, resumed-state equality, verbatim-render equality vs signed payload (breakdown lines included), Destination entered once *within a purchase* and never re-asked (across purchases it is re-entered by design — the chat stores no PII, and the sidecar may prefill only from this Consumer's own last order on that domain), first-time enroll-and-tap costing one ceremony, both expiry messages present and correct for their sweep, and a chat-side PII sweep asserting no Destination or Contact Point survives in the session DB, logs, or model context after a thread ends.
- DONE WHEN: toggle proves all four envelopes against the same core transcript; every badge's deviation text is asserted present; smoothness suite green; any agent freelancing (reworded/invented totals, skipped checks, tapless finish) fails conformance display with a named code.
