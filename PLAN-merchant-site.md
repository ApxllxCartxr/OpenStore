# Plan — Demo Merchant Site (`demo/merchant-site/`): SpoiledDuckie

Surface 2. Proves a Merchant can operate the sidecar. SpoiledDuckie is a real accessory shop, not a CRUD demo: Next.js + Postgres in its own container and compose service — deliberately a different stack from the sidecar to prove HTTP-only integration. Own DB is the Merchant truth the sidecar mirrors. Manually-set prices only — no offers/discounts *engine* (cut per grill Q44) — plus the pricing a real shop cannot skip: shipping zones with flat rates, per-item GST, and a hand-entered discount code table with no rules behind it, all served through door 9 `quote` (ADR-0010).

## M1 — SpoiledDuckie storefront + schema + seed

- Storefront (industry-standard, shopper-facing): home (hero + featured + search), shop (category/tag/price/availability filters, ordered results, pagination), item = the Product Group page (gallery, colour/size picker over the group's axes, add-ons like gift-wrap + extra charm), where picking resolves to exactly one Catalogue Item before `Add` is enabled — its price, its stock state `in-stock / low-stock / sold-out`, its verbatim price, with unavailable combinations shown as such rather than hidden — direct Add + direct checkout, Buy-via-agent hint with sidecar card URL), direct cart/checkout (site-direct: the storefront's own cart holds stock for 30 min before any order row exists — Woo's `hold-stock` pattern — so an abandoned browser cart cannot leak inventory, and `available` drops immediately as SPEC §5 says. **This path takes no payment**: a second money path is forbidden (SPEC §9), so a direct order is created only when the shop confirms it and is marked paid by hand in demo-admin, exactly the "recorded manually for direct buyers" case SPEC §6 already names. Address + shipping option + GST render from the same breakdown the agent flow gets), order lookup by unguessable token only — never a sequential order number, and a lookup by human order number additionally requires a matching Contact Point under a throttle, because a guessable lookup key is an IDOR that hands strangers other people's addresses. SEO slugs, schema.org `ProductGroup` + `hasVariant` + per-variant `Offer` JSON-LD on every group page (this is what crawlers and AI channels actually read, and it belongs with the pages that own the SEO — the sidecar's `/agent/feed.json` mirrors the same facts for the exposed subset in Merchant Center attribute names; both publish the shopper-facing price consistent with the tax-inclusive flag, since India requires tax-inclusive prices in feeds and a JSON-LD `Offer.price` that excludes GST understates every listing), responsive, accessible, named empty/error states.
- Postgres with migrations.
- Tables: `product_groups` (slug unique, name, description, media JSON, `option_axes` JSON — the axes and their allowed values, e.g. colour/size — tags, status `active/archived`; presentation only, never sellable and never referenced by a cart line), `catalogue_items` (sku unique, `group_id`, `options JSON` = this item's *resolved* values on the group's axes with a unique constraint per group so one combination cannot exist twice, name, price_minor int ≥ 0, tags, media JSON, status `active/archived`, low_stock_threshold, `hsn_sac`, `gst_rate_bp` int — price, stock, and threshold live here and never on the group), `shipping_zones` (name, matcher on postal code / state / country, flat `cost_minor`, ETA days), `discount_codes` (code unique, `amount_minor` or `percent_bp`, active window, per-order cap, `visibility` `public/private`, `max_uses` (private defaults to 1), `uses_count` — a hand-entered table, never a rule engine), `code_reservations` (code, order_id, state, unique on code where held — the row that makes single-use codes race-safe inside `reserve`), `merchant_tax_identity` (GSTIN, registered state, price-inclusive flag, `invoice_prefix` — the Merchant-set first segment of ADR-0020's `{prefix}/{financial year}/{sequence}`, which otherwise has nowhere to live), `stock` (one row per Catalogue Item — per variant, not per group — int ≥ 0, no nulls; row missing or negative fails loud), `stock_moves` (append-only: when, sku, delta, channel `site-direct / agent-reserve / agent-commit / agent-release / refund / restock / admin-adjust`, actor, reason), `orders` (the 8 canonical statuses: `pending / confirmed / paid / cancelled / expired / failed / refunded / completed`, line items `{sku, qty, price}`, the pinned Quote breakdown, `refunded_minor` (full vs partial is derived, never a ninth status), Destination + Contact Point + options inside the row as the only plaintext copy with a retention window and an erasure action that is refused while the order is live and allowed only on a terminal status (ADR-0011), `agent_id`, `consumer_id`, `cart_hash`, `quote_hash`, `attestation_hash` (pinned per SPEC §4 so later catalogue edits cannot rewrite history), `order_salt` 128-bit (the HMAC key for the evidence PII commitments — lives here and nowhere else, and dies with the row, ADR-0011), `tracking_number` + `carrier` + `dispatched_at` (all nullable, set together by a dispatch record independent of order status — a COD order can dispatch while still `confirmed`, before `paid` exists), `invoice_number` (nullable until dispatch, unique, assigned from `invoice_sequences(financial_year, next_number)` by atomic increment on the first dispatch record only — never re-derived, never reused; `financial_year` is the April–March year of `dispatched_at` evaluated in `Asia/Kolkata`, never in UTC, or a dispatch late on 31 March files into the year that just closed and opens a gap in both — ADR-0020), `erased_at`, `expires_at` set by sidecar (one column, two deadlines — the `pending` Quote-validity sweep and the `confirmed` payment window — always meaning "the next deadline the sidecar will act on"), `authority` (kind + Binding, replacing what was a passkey-shaped `tap_proof`), the payer handle as the third plaintext PII field under the same retention window and erasure action as Destination and Contact Point (ADR-0011), `receipt_id` 128-bit), `refunds` (order_id, `amount_minor`, reason, per-line restock flags, provider refund ref, created_at — multiple partials are legal now, so a single `refunded_minor` scalar cannot hold the history or reconcile against the Provider; `refunded_minor` on the order is the derived sum).
- Seed: 12 SpoiledDuckie Product Groups (tote, cap, sticker pack, keychain, hair clips, phone charm, pin set, plush mini limited 10, charm-bar seat service slot 10, gift-wrap add-on, extra-charm add-on, one `recalled`-tagged item to demo the blocked check) expanding to ~20 Catalogue Items — the tote in two colours, the cap in two sizes, one group with a deliberately unavailable combination (black/L never made), and the rest single-item groups — so the picker, per-variant stock, and `item_group_id` all have something real to exercise with counts on every SKU incl. a `limited`-tagged line capped at 2 per order, plus one 24h-pending example order. Seed also carries the tax identity (GSTIN, registered state), per-item GST rate + HSN/SAC, two shipping zones (intra-state and inter-state, so both GST splits are exercised), one unserviceable postal range, and one hand-entered discount code. - Compose service + health endpoint. No imports from sidecar or buyer-chat — not even types.
- DONE WHEN: store boots alone, seed loads with zero null-stock rows, catalogue validation rejects missing/negative/float stock or a missing GST rate/HSN with a named error; shop renders home → shop → group page → variant resolved by the picker → direct checkout (with shipping + GST on the total) → lookup with zero sidecar imports; an unavailable combination renders as unavailable rather than 404 or silently absent.

## M2 — Shop-ops admin (demo-admin, industry-standard tools, v1-scoped)

- Access control first: demo-admin is session-authenticated (single Merchant operator, password hashed with argon2id, CSRF on every mutation, no public route) and bound to the private network in compose. It holds the Refund button, which moves real money through the sidecar — an unauthenticated admin is a refund endpoint for anyone who can reach the container, which is the one hole a demo must not ship.
- Dashboard: open orders, `refund-requested`, low-stock, `failed/sold-out` counts.
- Catalog: group CRUD (axes, media, copy, slug) plus a variant matrix beneath it — generate combinations from the axes, then set price, stock, threshold, HSN/SAC and GST per Catalogue Item, leaving combinations that were never made absent rather than zero-stocked. `active/archived` at both levels (no hard delete with orders), bulk archive, CSV import/export carrying `item_group_id` + resolved option columns so a round-trip preserves the grouping.
- Pricing setup: shipping zones (matcher + flat cost + ETA), GST identity (GSTIN, registered state, inclusive/exclusive) and per-item rate + HSN/SAC, discount code table (add/expire/deactivate by hand) with `visibility` (`public`/`private`), `max_uses` (private defaults to 1), and a minimum-entropy check refusing guessable private codes at creation (ADR-0015). Every field is a typed value a human enters; anything shaped like a rule, tier, or auto-apply fails review (SPEC §13).
- Inventory: adjust with reason + actor, moves audit with channel filter, low-stock thresholds + badge, restock.
- Orders: searchable/filterable list, detail with Timeline (status history + Transcript ref + moves + receipt link + invoice number once assigned), a dispatch action recording an optional tracking number + carrier — available from `confirmed` onward and refused on `cancelled` / `expired` / `failed` with `dispatch-not-allowed`, since an order whose goods never left must never burn a sequence number (ADR-0020), and otherwise independent of the ship-owned status transitions, so a COD order can dispatch before it is `paid` — that assigns `invoice_number` on first use and fires the shipped notification, plus the ordinary shop-owned status transitions (reject `pending/confirmed` → `cancelled` with reason; mark `completed` once fulfilment is closed out; Cancel hidden once `completed`), Refund button on `paid/completed` → dialog (reason + amount defaulting to the full remaining and capped at it + per-line `[x] return stock to sale` + notify toggle) calling sidecar refund; partial refunds show as `Refunded ₹X of ₹Y` on a still-`refunded` order; one `refund-requested` queue fed by agent requests via sidecar and manual entries for direct buyers. Status flip alone never moves money; V1 allows partial amounts (capped at the remaining captured) but no fees, cancellation charges, or store credit.
- Validation: price/stock integers only, negative refused, unknown SKU refused, GSTIN checked for the 15-character state-code + PAN + entity shape, all failures named. Every stock move in `stock_moves` (who, when, delta, channel, reason).
- Explicitly not here: discount *engines* and campaigns (the flat code table is here; rules are not), customer accounts, keys, provider secrets, policy signing, exposure policy, receipts — those are the sidecar `/agentic` console or phase-two. Demo-admin is shop ops only so the demo stays replaceable.
- DONE WHEN: full ops loop passes in tests — create item → set GST + zone → set stock → place test order → adjust → cancel / partial refund / full refund — with the audit showing every move and over-refund refused; bulk/CSVs covered; an order recording dispatch gets exactly one gapless `invoice_number` for the current financial year and a second concurrent dispatch call on the same order cannot double-assign one; a COD order can record dispatch, tracking number, and its `invoice_number` while still `confirmed`, before it is `paid`; dispatch on a `cancelled`, `expired`, or `failed` order is refused with `dispatch-not-allowed` and consumes no sequence number; a dispatch recorded at 23:45 IST on 31 March takes the *closing* financial year's sequence and one at 00:15 IST on 1 April — still 31 March in UTC — opens the new year's sequence at 1 rather than continuing the old one; dispatching without a tracking number is allowed and dispatching with one attaches it to the order and fires the notification.

## M3 — Trait implementation (the 9 doors)

- Implement the sidecar's trait natively over HTTP on the private network: `catalog.read / stock.read / reserve / commit / release / restock / orders.create+read / orders.set-status / quote`, HMAC auth + idempotency keys, closed reason codes. `catalog.read` returns Product Groups with their axes and each group's Catalogue Items with resolved options, price, and HSN/GST — a shape an agent can render as a picker and can never mistake for a sellable group. Any door taking a `sku` refuses a group id with `variant-required`. `stock.read` returns exact integers per Catalogue Item — it is a private-network door between this store and its own sidecar, and the sidecar is what buckets before anything reaches an agent (SPEC §5).
- `quote` (door 9, ADR-0010): given lines + Destination (+ optional option id and code), return subtotal, discount lines, Add-on amounts folded into their parent line rather than standing alone (composite supply: the parent's rate, HSN/SAC, and Place of Supply apply, so gift-wrap on the charm-bar seat is taxed as that service and gift-wrap on the tote as goods; an orphan Add-on refuses with `addon-without-parent`), the zone's fulfillment options with cost + ETA, GST lines split CGST/SGST or IGST **per line** — goods compare the registered state to the Destination state, a service sold at the premises is always taxed where it is performed, so a mixed basket can carry both splits at once — honouring the tax-inclusive flag — inclusive (Indian MRP, the common case) means the tax lines are *informational and already inside the subtotal* and must not be added again, exclusive means they add; getting this backwards double-charges every order, so both directions are seeded and tested — and the total — paise integers, sign intrinsic, byte-identical for identical inputs, zero side effects.
- Three pricing rules that decide whether the invoice is legal, all pinned here because two implementations that guess differently will trip the Gate's `quote-inconsistent` check: **delivery is taxed** (a delivery charge follows the principal supply, so the fulfillment amount is apportioned across lines by taxable value and taxed at each line's own rate and Place of Supply — it is never a tax-free line); **discounts apportion the same way** before tax, so a `percent_bp` code on a mixed-rate basket reduces each line's taxable value rather than the total after tax; and both apportionments use **largest-remainder** so the parts sum exactly to the whole with no orphan paise. **Rounding** is half-up to the paise at line level; any rupee-level rounding the Merchant wants appears as an explicit `round_off` line so the breakdown still sums to the total exactly. Every rejected code — unknown, expired, exhausted, ineligible, or private-presented-through-an-agent — refuses as the same `code-invalid` with no distinguishing message or timing, so door 9 is not a code oracle. A code is reserved inside `reserve` under the existing idempotency key and returned by `release`, so two concurrent baskets cannot spend one single-use code and no tenth door appears. An unserviceable Destination refuses with `destination-unserviceable`. This door is the only place in the repo where money is computed.
- Semantics: `reserve` is atomic compare-and-set (fails `sold-out` if `available < qty`, `CHECK (available >= 0)`, never negative); `commit` decrements `available` on paid; `release` returns on cancel/expire/fail — including the `confirmed` payment-window sweep, which is the common case in practice, not an edge one; `failed` auto-restores reduced stock; `restock` takes the refund's per-line flags and returns only the lines ticked (a refund with no line ticked moves no stock), matching the per-line dialog in M2 and SPEC §6. A COD order holds stock through `reserve` like any other and settles through `set-status` at delivery or RTO — the money side lives entirely in the sidecar's Ledger (ADR-0018) and this side never writes it. Direct site sales decrement `available` directly — the sidecar sees them on its next fresh read. V1 never oversells.
- Shop-initiated transitions on a sidecar-created order (reject → `cancelled`) call the sidecar over HMAC exactly as Refund does — never a direct write to this side's own row. The sidecar holds the `RESERVE`, so a local write would strand a Ledger hold and drift stock; routing through the sidecar also serialises shop-reject against a Consumer tap and the expiry sweep on the same `set-status` key, which is the race that otherwise sells the last unit twice.
- Pass the sidecar's trait conformance suite (from Sidecar S2) unmodified: retries collapse, double-commit impossible, release-without-reserve refused, 50-concurrent-on-5-units yields exactly 5 holds with stock never negative.
- DONE WHEN: conformance green against this real implementation, including quote determinism across repeat calls, intra-state vs inter-state GST split correctness, a mixed goods+service basket carrying both splits in one Quote, gift-wrap inheriting its parent's rate and POS in both directions, an orphan Add-on refusing, a group id sent where a SKU belongs refusing with `variant-required`, two variants of one group holding independent stock (selling out black leaves red buyable), and a two-per-order cap on a `limited` group refusing three units spread across its colours, two concurrent baskets racing one single-use code yielding exactly one winner, an unserviceable Destination and an expired code each refusing by code, a delivery charge taxed and apportioned across a mixed-rate basket with the parts summing exactly to the whole, a percent code apportioned pre-tax, a shop-reject racing a tap resolving to exactly one outcome with no stranded hold, plus a simulated walk-in sale visibly lowering the next agent gate's `available` and an abandoned storefront cart returning its held stock at 30 min.

## M4 — Notifications (to the sidecar and to people) + health

- Emit signed change events the sidecar treats as triggers only (`stock.changed` on `available` change, `order.changed` for sidecar consumption only — never pushed to chat): HMAC-signed, `event_id` dedupe, out-of-order safe, replay-safe. The gate still re-reads fresh plus a periodic reconciler poll — events are a speedup, never the source of truth.
- Consumer and Merchant notifications, owned here because this side owns customer comms and the only Contact Point plaintext (SPEC §10): an "order received, awaiting payment" notice on `confirmed` and the confirmation proper with the receipt link on `paid` (calling an unpaid order confirmed is how support queues fill), a shipped notice carrying `tracking_number` + `carrier` + `invoice_number` fired at dispatch — whenever the Merchant records it, independent of order status, so it can precede the `paid` notice on a COD order — refund notice with amount on `refunded`, expiry notice on `expired`, and a new-order alert to the Merchant. Pluggable sender with a log-only default so the demo needs no external account; templates render the Quote breakdown verbatim, never a recomputed total.
- Liveness/readiness endpoints for compose + proxy.
- DONE WHEN: event replay/duplication/reorder tests pass; killing events degrades to slower reads with zero wrong sales; each status change fires exactly one notification (idempotent on retry) carrying the verbatim breakdown; a dispatch record fires exactly one shipped notice however many times it is retried — dispatch is deliberately not a status change, so it needs its own idempotency assertion rather than inheriting that one — and an erased Contact Point skips send with a named reason instead of throwing.

## M5 — Compose wiring + manual pricing discipline

- Compose service with its Postgres, env-driven secrets (local `.env` only), no shared volumes/DB with sidecar or chat. Reuses the reference `Caddyfile` from Sidecar S7 unmodified; adds `/healthz` + `/readyz` for proxy checks.
- Pricing discipline enforced in review: every price, zone rate, GST rate, and discount code is a typed value a human entered — no rule, bot, tiering, auto-apply, or draft code anywhere in this repo path. Door 9 may look up and add those values; it may not derive new ones. Any engine-shaped code fails review by rule, not by test.
- DONE WHEN: `store + sidecar` compose boots via the path split, seeded SpoiledDuckie charm orderable through the sidecar gate against this store's live stock; admin is unreachable without a session from outside the compose network; a notification fires exactly once per status change with the verbatim breakdown.
