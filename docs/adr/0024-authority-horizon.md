# Tap-every-time is v1 because nothing testable exists yet, not because autonomy is the enemy

ADR-0008 removed spending authority from agents and ADR-0017 made `confirm` refuse without a fresh human Authority. Both are right and neither changes here. But the reasoning around them has been drifting toward a principle — *a human taps for every spend, always* — and that is not the decision that was actually taken. Written down now, before the drift hardens into an architecture nobody remembers choosing.

Two different things have been travelling under one banner, and only one of them is a principle.

**Refused permanently: an agent holding a spending credential issued by a commerce platform.** A token a Consumer grants once that an agent later spends without them, held by a foreign platform, outside the banking rails, with that platform's own recourse story. That is ADR-0008's actual target and ADR-0013's actual refusal, and no amount of market pressure reopens it. The refusal is the product.

**Deferred for lack of a testable rail: authorization without a per-purchase human tap.** A capped, revocable mandate held in the bank and NPCI stack, where the rail authenticates and the merchant's Gate still decides deterministically, is a different object from the credential above — ADR-0016 says so already. It is not refused. It is unbuilt, and the honest reason is availability, not conviction: NPCI's Unified Agent Protocol has no published limits or authentication model, no sandbox exists to develop against, and there is no agent-finance platform offering anything equivalent that a small team could integrate and test today. You cannot build against an unpublished spec and you certainly cannot prove a money path correct without one to test.

That distinction matters commercially, because the second category is where the market goes. Fully autonomous purchasing — an agent that buys within limits its owner set, without a per-purchase interruption — is not a fringe case to concede politely. If it becomes how people buy and this system can only express a tap, this system is where commerce used to happen. Conceding the low-value high-frequency band (ADR-0016) was a judgement about *today's* rails, priced against a delegation model we refuse. It was never a decision to sit out autonomy itself.

There is also a nearer route than UAP, found while retiring the Reserve Pay COD path (ADR-0018). Reserve Pay is a standing reserve: a Consumer blocks up to ₹10,000 for up to 90 days at one merchant, and each purchase debits it instantly *at the customer's own action on the merchant's platform* (NPCI/UPI/OC-228/2025-26, 8 October 2025). The human is still in the loop — so ADR-0008 holds untouched — but what they do per purchase is press buy on the merchant's own domain rather than enter a PIN in a banking app. That is a real reduction in friction on a sanctioned rail, in exactly the band NPCI aims the feature at and exactly the band this product currently concedes. It is not v1: a reserve spanning several orders does not fit the per-order `RESERVE`/`CAPTURE`/`RELEASE` shape escrow-zero is built on, and making it fit is money-core work needing its own ADR.

What this ADR fixes is the seam, so that arrival is an adapter rather than a rewrite. Already in place and to be preserved deliberately rather than by luck: the authority closed set with `mandate` defined, registered, recorded in the Transcript and refused with a named code (ADR-0016, ADR-0017); the Gate as the deterministic authorizer whatever authenticated upstream, which is the property that survives every one of these routes and the one NPCI's own chairman describes; and provider-declared methods (ADR-0013), so a new rail lands as an adapter declaring a capability. The Provider trait's unused `block`/`capture-block`/`release-block` capability stays for the same reason.

Revisit when any of these becomes true, and treat it as a trigger rather than a nice-to-have: UAP publishes limits and an authentication model with a sandbox to test against; an acquirer offers Reserve Pay's repeat-purchase shape self-serve; or any rail offers a capped, revocable, bank-held mandate that can be integrated and proven correct in a test environment. Each of those turns "we cannot test it" into a false statement, which is the only thing currently holding the decision in place.

Consequences: no change to v1 — the Gate, the closed authority set and every refusal stay exactly as specified, and nothing here licenses building against an unpublished rail. What changes is the framing that gets repeated outward: this system declines agent-held platform credentials, and has not yet implemented rail-held mandates because none is testable. Any external material that states the first as "a human must always tap" is overclaiming a permanence the design does not have, and should be corrected the way `docs/REVIEW-remediation.md` item #3 corrects the reach claim. The repeat-purchase design and the mandate path each need their own ADR before any of either is built.
