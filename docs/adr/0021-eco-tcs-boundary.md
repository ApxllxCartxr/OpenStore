# Why OpenStore likely isn't an Electronic Commerce Operator under GST

CGST Act Section 52 requires a platform to collect TCS (0.5%) and file GSTR-8 when it is an "electronic commerce operator" — read: it collects payment on behalf of the sellers using it, the Amazon/Flipkart marketplace shape. Worth stating out loud because the sidecar sits between Consumer and Merchant in every transaction and could look like that shape from a distance.

It isn't, on the architecture as specified: payment lands directly in the Merchant's own Provider account (Razorpay/Justpay/Airpay — SPEC §2, "Payment Provider (the Merchant's...)"), the sidecar never custodies funds, and the Provider trait's `make-link`/`check-status`/`refund` primitives (PLAN-sidecar.md S3) never route money through anything OpenStore controls. The Merchant's own Provider account is the counterparty for the payer's bank, not the sidecar. That is the same structural reason ADR-0007 gives for single-tenant deploys (no shared money, no shared DB) — it was chosen for a different reason and produces this property as a side effect.

Said the way ADR-0016 says its own open regulatory question: this is a read, not a ruling — where "facilitates supply" starts and stops under Section 52 is a matter for a Merchant's own tax counsel, not an argument this document gets to win. What is fixed here is the property that makes the read plausible: no version of this system that routes payment through an OpenStore-controlled account should ship without revisiting this ADR first, because that would be the change that actually triggers Section 52 exposure — not a hosting or deployment detail, but a design choice worth its own grill.

Consequences: none to the code — this documents a boundary the payment-routing architecture already holds, not a new requirement. Revisit if a future Provider adapter or hosted-mall design (`PLAN-distribution.md`, phase two) ever has funds settle anywhere but the Merchant's own account.
