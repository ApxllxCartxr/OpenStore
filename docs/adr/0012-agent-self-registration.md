# Strangers may register themselves; only the tap spends

SPEC §2 promises any Buyer Agent can transact with the sidecar, while SPEC §7 issued OAuth credentials only by prior Merchant action — a stranger arriving cold could not get a token. Shopify closes the same gap with agent profiles, signed requests, and trust tiers that unlock in-agent purchase completion for high-tier agents.

We close it differently, and more simply, because our spend authority never rests on the agent: an unknown agent publishes a profile at a well-known URL carrying its name, contact, and ES256 JWKS; the sidecar verifies a signed request against that key on every call and issues a short token for all four scopes on the spot. No tier unlocks money, because `confirm` is gated by a fresh `cart_hash`-bound Consumer tap (ADR-0008) and nothing else. Reputation buys throughput, not authority: self-registered agents get the low rate-limit tier, a Merchant-allowlisted agent gets the high one, and a Merchant blocklist entry refuses registration outright.

Nothing here is newly invented: request signing is RFC 9421 HTTP Message Signatures over method, target, `Content-Digest` (RFC 9530), `created` and `expires`, with a nonce and a short acceptance window to kill replay, and `agent_id` is the RFC 7638 JWK thumbprint. The one genuinely new attack surface is that a stranger can now make the sidecar fetch a URL of their choosing, so the profile fetcher is SSRF-hardened by rule (HTTPS only, public IPs only, metadata and private ranges refused, resolve-then-pin against rebinding, no cross-host redirects, size and timeout caps, its own rate limit).

That rule refuses the demo's own chat, which lives at a compose-internal address, so self-registration would be unprovable on the one deployment anyone actually runs. The exception is a dev-mode allowlist of named hosts (`OPENSTORE_DEV_PROFILE_HOSTS`), never a CIDR and never a blanket permission for private ranges, and it is fenced on every side: the cloud metadata address is refused unconditionally even in dev, resolve-then-pin and the redirect, size and timeout caps are unchanged, each use logs a warning and shows in health output and the console banner, and a non-empty allowlist alongside live provider keys refuses at boot. Naming individual hosts rather than unlocking a range keeps the blast radius to exactly the thing the demo needs; being unbootable in production keeps it from becoming the way strangers reach internal services.

Consequences: `agent_id` becomes the profile's key thumbprint for strangers and the issued client ID for allowlisted agents; both are revocable and both land on the order (ADR-0004 dual identity is unchanged). The onboarding claim in SPEC §2 becomes true as written. Accountability survives: a stranger is anonymous to the Merchant but pseudonymous forever to the ledger, and abuse is throttled by tier rather than by admission.
