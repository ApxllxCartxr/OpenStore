# Merchant quotes the money, sidecar verifies it

Shipping, tax, and discount codes are three ways of asking the same question: what is this basket's final total for this Consumer at this address? V1 answers it with one new trait door (`quote`, door 9) rather than three sidecar features. The Merchant computes the whole priced breakdown — subtotal, discount lines, fulfillment options and the chosen option's cost, tax lines (GST: CGST/SGST or IGST by place of supply), total — because the Merchant already owns prices, zones, GSTIN, HSN/SAC, and whatever code table they run (ADR-0001). The sidecar computes none of it and ships no rate table, no tax engine, and no discount engine (SPEC §13 still forbids all three inside the sidecar).

Verification replaces computation: the Gate re-calls `quote` with the same inputs immediately before any money move and byte-compares the result against the Quote pinned in `cart_hash`. Any difference fails closed with `price-changed` and the Consumer re-taps on the new number. A Merchant discount code is therefore *validated by the Merchant*, never interpreted by the sidecar, which is how codes arrive in v1 without an engine.

Consequences: the trait is 9 doors, not 8 — SPEC §5, Sidecar S2, Merchant-site M3, and the conformance suite move together. `cart_hash` canonical bytes now cover the Quote and the destination (SPEC §4), so the freeze must happen after this lands, not before. A Merchant who implements only flat pricing returns a Quote with zero-value fulfillment and tax details and everything else holds. UCP's totals breakdown (`subtotal / items_discount / fulfillment / tax / total`) maps 1:1 onto the Quote, so the S6 translators gain no special cases.
