# A sequential tax invoice number, separate from the receipt ID

The sealed receipt bundle (ADR-0009) opens by a 128-bit unguessable `receipt_id` — deliberately unguessable, because a sequential order number is an IDOR that hands strangers other people's order pages (PLAN-merchant-site.md's order-lookup rule). But CGST Rule 46(b) requires a tax invoice to carry a consecutive serial number, unique per financial year, with no gaps — the opposite property. The spec text already calls the Quote breakdown "the invoice" in a few places (e.g. PLAN-sidecar.md's `quote-consistent` note: *"a legal invoice and a verifiable one stop being the same document"*) without ever specifying the artifact that makes that literally true for a GST-registered Merchant.

Decision: these are two different documents serving two different properties, and both exist. The receipt bundle stays unguessable and proves the transaction. A second field, `invoice_number`, is generated at **dispatch**, not at `paid`: CGST Section 31(1)(a) ties a goods invoice to removal of the goods, not to receipt of payment, and the two coincide only on the prepaid paths. ADR-0018's COD path breaks that coincidence on purpose — `cash-on-delivery` reaches `paid` only when cash is collected at the doorstep, after the goods have already moved — so an invoice generated at `paid` would be issued after removal on roughly 60% of Indian e-commerce, which is the one thing Rule 46 forbids. Dispatch is a Merchant-recorded event, not a ninth status: it can land while a COD order is still `confirmed`, well before `paid` exists, or any time after `paid` on a prepaid order. An order that is refunded before ever dispatching never gets a number, for the same reason as before — GST treats an unfulfilled advance as a receipt/refund voucher matter, not a tax invoice, so there is still no gap to explain. Format: `{merchant-set prefix}/{financial year, Apr–Mar}/{sequence}`, sequence monotonic within the financial year, assigned by an atomic increment (`invoice_sequences(financial_year, next_number)`, same compare-and-set discipline as stock) on the first dispatch record only, so two concurrent dispatch calls on the same order cannot collide or skip. Lives on the Merchant's own orders row — Merchant is truth (ADR-0001) — not in the sidecar, which computes no invoicing any more than it computes tax.

Consequences: SPEC §6 gains a dispatch clause, decoupled from any single status; PLAN-merchant-site.md gains the sequence table, the dispatch action, and renders the number on the receipt page and the shipped notification alongside the verbatim breakdown once it exists — the `paid` and `confirmed` notifications no longer carry it, since it may not exist yet at either point on a COD order. Full e-invoicing (IRN registration with the GST portal, mandatory above the turnover threshold) is a further step past this — this ADR only guarantees the number exists and never has a gap, which is the prerequisite for it, not the whole of it. That threshold-gated step stays phase-two and is not decided here.
